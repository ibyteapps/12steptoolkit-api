# Taking over 12steptoolkit.com

**The question this answers:** can Laravel serve the public website, with
`/console` inside it, the way `aabigbook.app` and BohriConnect do?

Yes — and not yet. This document is the gap between the two, measured rather
than estimated, so the decision to move the document root is made against a
list instead of a feeling.

---

## 1. What is at that document root today

`12steptoolkit.com` is a Next.js static export (`../Website`, built into
`Website/out`). Measured 2026-10-08:

| | |
|---|---|
| HTML pages exported | **212** |
| URLs in `sitemap.xml` | **169** — counted from the live sitemap, not estimated; the fixture is `tests/Feature/Site/fixtures/indexed-urls.txt` |
| of those, under `/aa-literature` | **180** |
| of those, `/blog/…` | **19** |
| Root pages | `/`, `/contacts`, `/get-app`, `/get-the-app`, `/privacy`, `/terms` |
| Section indexes | `/aa-literature`, `/aa-literature/big-book`, `/…/prayers`, `/…/readings`, `/…/stories-edition-1`, `/…/stories-edition-2`, `/blog` |
| Also served from that root | `sitemap.xml`, `robots.txt`, `ads.txt`, `app-ads.txt`, `reflections.php`, `/app/reset/*`, `/app/validate2/*` |

The literature is the site: 86 Big Book pages, 69 personal stories across two
editions, 11 prayers, 8 readings. That is what ranks, and it is a real archive
rather than marketing copy.

**What this application serves at `/` today:** one route, in
`routes/site.php`, rendering `site.placeholder`.

So the arithmetic of switching the document root today is 169 URLs in, one URL
out. Every other address returns the application's 404. Search engines drop a
404 within days and the recovery, if the pages come back under the same
addresses, takes weeks.

## 2. Three things that would break before the SEO did

Worth separating, because they hurt sooner and they are not about rankings.

* **`app-ads.txt`.** Google AdMob fetches `https://12steptoolkit.com/app-ads.txt`
  to confirm which sellers may sell inventory for the apps. If it 404s, the
  apps' inventory is treated as unauthorised and ad revenue falls. The file is
  one line and must be served from the root of the domain the store listing
  names.
* **`/app/reset/*` and `/app/validate2/*`** — six pages that are the landing
  pages for password-reset and email-verification links. Links already sent
  point at them. They are `Disallow`ed in `robots.txt`, so no ranking is at
  stake; what is at stake is somebody halfway through resetting a password.
* **`reflections.php`** — a PHP file sitting in the export, so whatever the
  document root is has to execute PHP there or stop serving it.

## 3. A defect that is already live, and is worth fixing either way

**69 stories are submitted to Google twice, under two different addresses.**

Every personal story exists at its clean address and again with the section
folded into the filename:

```
/aa-literature/stories-edition-1/a-close-shave              ← clean
/aa-literature/big-book/stories-edition-1%2Fa-close-shave   ← the same page
```

There are 69 of each and **all 138 are in `sitemap.xml`** — a third of the
submitted URLs are duplicates of the other two thirds. A slug containing a
slash is being URL-encoded into a filename by the export rather than nested.

This is not caused by anything in this rebuild and it does not block anything.
It is here because the takeover is the moment to fix it: in Laravel the clean
address is the only one that needs to exist, with a **301** from each encoded
form to it. Done at the same time as the move, the duplicates are consolidated
rather than merely dropped.

## 4. What has to be true before the document root moves

A checklist, not a plan — each line is a thing to tick.

1. **Every one of the 169 sitemap URLs answers 200 from Laravel at the same
   address.** Not "equivalent content at a tidier URL": the same address. A
   redesign is a separate argument to have after the move, not during it.
2. **Each page keeps its `<title>`, meta description and canonical link.**
   Whatever the export emits today is what ranks today.
3. **`sitemap.xml` and `robots.txt` are served** — generated by the
   application, not copied, or they go stale the first time a page is added.
4. **`ads.txt`, `app-ads.txt` and `reflections.php` still answer** at the root.
5. **The 69 encoded story URLs 301 to their clean address**, and the clean
   address is the only one in the new sitemap.
6. **`/app/reset/*` and `/app/validate2/*` answer**, still `Disallow`ed.
   They are served by the legacy PHP app, which lives *inside the document
   root* and is not produced by the Next build — the old deploy rsyncs with
   `--exclude 'app/'` so as not to delete it. Move the root and nothing
   serves it: every password-reset link already in somebody's inbox 404s.
   `docs/nginx/12steptoolkit.com.conf` carries a commented `location ^~ /app/`
   that keeps it answering from where it is; uncomment it in the same change
   that moves the root.
7. **`SITE_SERVES_WEBSITE=true` and `SITE_NOINDEX=false`** in `.env`. Both
   default the other way, because today this application does not own `/`;
   left as they are, the move would de-index all 169 URLs in a few days.
   `deploy.sh` **fails** the deploy once `SITE_SERVES_WEBSITE` is true and
   `noindex` is still on, so forgetting it is caught by a machine rather than
   by the traffic graph a week later.
8. **The smoke test in `deploy.sh` is extended** to cover a page from each
   section, the sitemap, `app-ads.txt` and one 301. The smoke test is how this
   list stops being a document and becomes a check that runs every deploy.
9. **`Website/out` is still on the server, one move away**, so the rollback is
   pointing the document root back at it.

Numbers 1 and 2 are the work; the rest is an afternoon.

## 5. The order, so that nothing is ever both live and wrong

1. Install the application in **`WEBSITES/12steptoolkit.com/api`**, a sibling
   of the document root, and graft `/console`, `/api/v2` and `/up` onto the
   domain with nginx (`DEPLOYMENT.md`, and the blocks in
   `docs/nginx/12steptoolkit.com.conf`). The document root does not move, the
   export goes on serving all 169 URLs, and `/console` is already inside the
   main website at `12steptoolkit.com/console`. **Nothing below is needed to
   get that far** — the list in §4 is only for the day `/` itself moves here,
   which may be never.
2. Port the pages into Blade. Prove each one through a path the graft already
   owns, or on a throwaway subdomain pointed at `api/public` — either way a
   half-finished literature section is visible to you and to nobody else,
   because `/` still belongs to the export.
3. Walk §4 with the smoke test extended.
4. Move the document root of `12steptoolkit.com` to
   `…/12steptoolkit.com/api/public`, set `SITE_SERVES_WEBSITE=true` and
   `SITE_NOINDEX=false`, remove the now-redundant graft blocks, run
   `app_update_toolkit --check`, then submit the new `sitemap.xml` in Search
   Console and watch coverage for a week.
5. **Rollback, at any point:** point the document root back at `Website/out`.
   The database is not involved, so there is nothing to undo.

## 6. What I would not do

**Serve the export from Laravel's `public/` as static files to "keep the URLs
alive".** It works for an afternoon and it means two copies of 212 pages, one
of which nobody rebuilds. Either the pages are Laravel's or they are the
export's.

**Move the root before the literature is ported, and 301 the gaps to `/`.** A
mass redirect to the home page is read as a soft 404, so the pages lose their
rankings exactly as if they had 404'd, and the home page gains nothing.
